# Windows Plus 1.5.4 の小天体軌道

2026-11-12、Apple M4 / macOS 26.6.2 上で作者配布の Windows Plus 1.5.4 build101013 のコピーを起動した。実行ファイルの SHA-256 は `48961f09019e0e43f23f2537752978dc16c563c807f5b048ba5b0448c0d2b457`。Boxedwine 26R1、Wine 11、OSMesa の softpipe で、実ウィンドウの所有 PID とウィンドウ番号を照合して撮影した。保存した旧版状態とウィンドウ PNG の SHA-256 は[フレーム表](legacy-orbits-frames.tsv)で照合できる。検証 Mac での原画像、実行用 Lua と集計は `local/verification/p4-legacy-orbits/` にある。

## 同梱データでの軌道表示

同梱の個別定義57本だけを個別軌道ディレクトリに置いた `real` 試行で、同梱 packed データと合わせて起動。太陽中心・JD 2451000.5・宇宙モード・視野角45°・`Camera:setEuler(0,0,0)` に固定した。`Asteroids.selectedOnly=true`、`hide('All')` と `show('Ceres')` または `show('Icarus')` で選び、名前と天体を表示したまま軌道だけを切り替えた。保存状態で番号1または1566と該当のカメラ距離を確認した。各切替を通常のイベントループに戻してから撮影し、同じ地図矩形の x=42…1634、y=261…1309（1,671,057物理画素）の RGB を比較した。

| 実天体 | 太陽からの視距離 | 軌道の切替で変わった画素 |
| --- | ---: | ---: |
| セレス | 28 AU | 16,278 |
| イカルス（e = 0.826783） | 16 AU | 8,183 |
| 同上 | 9 AU | 9,574 |
| 同上 | 6 AU | 10,536 |

[条件別の差分とハッシュ](legacy-orbits-arcs.tsv)。実登録・描画には角度、視距離、画角の影響がある。例えば別の `final` 試行でセレスを9 AUから見た地図では、同じ軌道スイッチの切替による変化は0画素だった。

## 旧 Plus の頂点の選び方

上記 SHA-256 の PE32 の同一小天体管理オブジェクトを、読取・頂点生成・OpenGL 描画の各経路で照合した。仮想アドレスは PE の ImageBase `0x400000` を含む。検証には `xcrun llvm-objdump -d --x86-asm-syntax=intel --start-address=... --stop-address=... mitakaPlus.exe` と PE セクションの定数読み出しを用いた。

| 旧 executable 内の仮想アドレス | 確認した処理 |
| --- | --- |
| `0x48bcfe`、`0x48bd7a`、`0x48bd95` | packed reader と個別 reader が管理オブジェクト `0x1081a80` に記録する。個別要素の a と e は各記録の `+0x48` と `+0x50` に入る。[既存の個別形式監査](../../investigation/native-plus/minor-planet-individual-format-audit.md) |
| `0x566770…0x5667b5` | 曲線の対象種別4が分岐表 `0xc33ca4` から `0x5667a5` に入る。分割数 `0xc8`（200）、曲線、同じ管理オブジェクトを渡して `0x5058b0` を呼ぶ。 |
| `0x505907…0x505985`、`0x505b34…0x505b38` | 0から199までの整数 i を順に使う。`0xc30aa0` の binary64 は 6.283185307179586。a、e、E=2πi/200 を位置関数に渡す。初点は近日点で、元期、現在日時、M0 を参照しない。 |
| `0x5374e0…0x537539`、`0x50599a…0x505acc` | 軌道面上の `(a(cos E−e), a√(1−e²)sin E, 0)` を求め、要素の回転行列と表示単位を適用し、3個の double を1頂点として順序を保って格納する。 |
| `0x5664e1…0x566652` | `glBegin(GL_LINE_STRIP)`、各頂点の `glVertex3dv` の後、格納列の先頭をもう一度送り `glEnd()` する。楕円は200個の異なる頂点、閉合を含め201頂点送信、200辺。 |

通常版 1.3.1 でも小天体曲線の生成に200分割が指定されている。旧 Plus の値は上記 1.5.4 自身で確認した。[通常版の呼び出し](../../vendor/mitaka/sources/official/mitaka_source/Mitaka/mtk_space_curve.cpp)・[位置式](../../vendor/mitaka/sources/official/mitaka_source/Mitaka/mtk_orbital_element.h)。

旧版の実画面に対し、セレス28 AUとイカルス16 AUの軌道線で共通の透視投影を校正し、校正に使わなかったイカルス9・6 AUの位置を検算した。切替前後の最大 RGB 差が6を超えた画素を使い、縦横2画素おきに、2〜15個の連続画素の差分輝度で重み付けした線中心を測った。各中心から候補の最も近い線分までの画素距離を測定した。基礎となる位置は原要素の `Rz(node) Rx(i) Rz(w)` と上式から計算した。校正の初期値は地図の中心。2軸の中心、焦点スケール、視線方向の深度スケール、面内回転、深度の2軸の傾きを最小二乗（soft-L1）で同時推定した。

9 AUの906箇所と6 AUの1,042箇所で、E等分200辺との距離の95パーセンタイルはそれぞれ **0.259 / 0.573物理画素**、平均近点角 M を200等分した場合は **1.309 / 1.926物理画素**。E等分128辺でも0.243 / 0.524物理画素なので、画像の精度だけで128と200は区別できない。200辺の根拠は旧版自身のループ、実画面は曲線上の位置の確認である。[比較した候補と残差](legacy-orbits-projection.tsv)。

## 平均運動と非楕円の対照

`final`、`extra`、`n-hyper` は観測用の個別定義を加えた旧版の別起動である。正規57件に n のみや非楕円の定義はない。セレスの元データ（元期2451000.5、a=2.766180 AU、e=0.077887）について名前・番号を独立にし、aのみと `n=0.985607669/a^(3/2)`（度/日）のみを比較した。別の対照には a=1.5 AU を使った。

- JD 2451000.5 と 2451150.5 の旧版注視高度は実セレス・aのみの複製・nのみの複製で **39.3429° / −61.4659°**。a=1.5の2例では **48.6325° / 9.66039°**。どちらも同一組内の保存方位・高度が一致した。1.5 AU 組は軌道切替で変わる14,628画素の位置も強度も一致し、地図全体で差分画像どうしの RGB 差は0。名称や番号そのものは別である。
- eだけを1または1.2にした定義を旧版で選ぶと、選択パネルに独立した名前・番号が表示された。たとえば初日の e=1 の `P4Parab` は 980006。2日時の注視高度は e=1 で **−6.60144° / 54.9892°**、e=1.2 で **−67.9355° / 33.0494°**。追加の2日時では旧版の位置式が使う未正規化の平均近点角が負、または360°超になる条件を確かめた。地上視点の保存値は `Planet.Earth`。この試行の指定地点名や緯度経度は保存されていない。注視方向の測定だけでは開軌道の範囲・軌道線・近日点通過時刻・物理時系は確定しない。

- e=1.2 ではさらに、aのみ（番号980007）・nのみ（980008）の2通りを別起動で直接選んだ。両方の日付でカメラの保存方位・高度は全桁一致した（生の保存値136.875° / −67.9355°、243.213° / 33.0494°）。

実ウィンドウ比較図は検証 Mac の `local/verification/p4-legacy-orbits/legacy-orbit-windows.jpg`。Windows 実機や他の版はこの比較の対象外である。
